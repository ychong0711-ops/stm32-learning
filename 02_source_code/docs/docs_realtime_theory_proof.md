# 실시간 이론의 수학적 증명 — 태스크셋 스케줄가능성 분석

> **대상**: `main_fixed.c` (FreeRTOS 임베디드 예제, 수정판) + `bsp/` (STM32F4 HAL)
> **목적**: 코드의 우선순위 배정을 "감"이 아니라 **수학으로 증명**하고, 스케줄가능성을 정량적으로 입증
> **결론 요약**: 전체 이용률 **24.30%**, Liu–Layland 상한(73.48%)과 Bini 쌍곡선 상한(1.2618 ≤ 2) **모두 통과**, 전 태스크 **스케줄가능** ✅

## 0. 개요

독일 자동차 임베디드 대학원(특히 연구 중심 TU)에서 이 코드의 가장 큰 약점은
**"우선순위를 왜 그 값으로 배정했는가"에 대한 수학적 근거가 없다**는 점이었습니다.
이 문서는 다음 순서로 그 근거를 완성합니다.

1. 시스템 모델을 수학적으로 정의하고
2. 실시간 스케줄링의 핵심 정리 4개를 증명(스케치)하고
3. 응답시간 분석(RTA) 방정식을 유도하여
4. 실제 태스크셋에 적용해 숫자로 판정합니다.

계산은 동봉된 `rta_analysis.py`로 수행했으며, 모든 수치는 재현 가능합니다.

## 1. 시스템 모델과 가정

### 1.1 태스크 모델

태스크셋 Γ = {τ_1, τ_2, ..., τ_n}. 각 태스크 τ_i는 다음 파라미터를 가진다.

| 기호 | 의미 |
|---|---|
| T_i | 주기 (산발 태스크는 최소 도착 간격) |
| C_i | 최악 실행시간 (WCET, Worst-Case Execution Time) |
| D_i | 상대 데드라인 |
| p_i | 우선순위 (FreeRTOS에서는 **숫자가 클수록 높음**) |
| U_i = C_i / T_i | 이용률 |
| hp(i) | τ_i보다 **높은** 우선순위 태스크들의 집합 |
| B_i | 차단시간 (우선순위 역전으로 인한 최대 대기) |

### 1.2 가정 (Liu & Layland 표준 가정 + 코드 반영)

1. **선점형 고정 우선순위 스케줄링** — FreeRTOS는 preemptive, 고정 우선순위.
2. **암시적 데드라인 D_i = T_i** — 단, 워치독은 D_w = 1000ms(IWDG 타임아웃) > T_w = 100ms 예외.
3. **독립 태스크** — 큐/뮤텍스 상호작용은 §5의 차단시간 B_i로 흡수.
4. **제로 오버헤드 문맥전환** — 문맥전환 시간은 C_i에 포함시키거나 여유로 보정(§8 실측).
5. **우선순위 상속 뮤텍스** — FreeRTOS `xSemaphoreCreateMutex()`는 우선순위 상속 제공.

## 2. 핵심 정리와 증명

### 정리 1 — 임계 순간(Critical Instant) 정리

> **명제.** 고정 우선순위 선점 스케줄링에서, τ_i의 한 작업의 최악 응답시간은
> **그 작업과 모든 고우선순위 작업이 동시에 릴리스되는 순간**에 발생한다.

**증명 스케치.** τ_i의 작업 릴리스 시각을 t = 0이라 하자. 어떤 고우선순위 태스크
τ_j의 작업이 시각 a > 0에 릴리스된다면, 그 작업을 a = 0으로 **당겨도** τ_i가 보는
간섭은 줄어들지 않는다. 왜냐하면 작업을 앞당기면 τ_i가 실행될 수 있는 구간 [0, R_i)
안에 들어오는 τ_j의 작업 수가 **같거나 증가**하기 때문이다. 따라서 간섭은 "모두
동시에 릴리스"일 때 최대가 되고, 이때 응답시간이 최악이 된다. ∎

### 정리 2 — RMS(Rate-Monotonic) 최적성 정리 (Liu & Layland, 1973)

> **명제.** D_i = T_i인 태스크셋에 대해, **어떤** 고정 우선순위 배정으로도 스케줄가능하다면
> **RMS 배정**(주기가 짧을수록 우선순위 높음)으로도 스케줄가능하다.

**증명 스케치 (교환 논증, swap argument).** RMS 순서를 어기는 **인접한** 두 태스크
τ_a, τ_b (T_a > T_b 인데 τ_a가 τ_b보다 높은 우선순위)를 잡아 서로 교환하자.
긴 주기의 τ_a가 짧은 주기의 τ_b를 방해하는 것보다, 그 반대(τ_b가 τ_a를 방해)가
스케줄가능성에 덜 해롭다 — τ_b는 더 자주, 더 촉박하게 실행되어야 하므로 방해를
받으면 안 되고, τ_a는 주기가 길어 흡수 여유가 크다. 이 교환은 스케줄가능성을
보존하며, 이를 반복하면 RMS 순서에 도달한다. 따라서 RMS가 최적이다. ∎

> 📌 **의미**: 우리 코드의 우선순위는 RMS와 거의 일치해야 하고, 예외가 있다면
> 반드시 별도로 정당화되어야 한다 (§6에서 워치독 예외를 증명).

### 정리 3 — Liu–Layland 이용률 상한

> **명제.** n개의 태스크에 대해 다음이 성립하면 RMS로 스케줄가능하다(충분조건).
>
> ```
> Σᵢ Uᵢ  ≤  n(2^(1/n) − 1)
> ```
>
> n → ∞ 일 때 우변은 **ln 2 ≈ 0.693**으로 수렴한다.

**증명 스케치.** 정리 1에 의해 최악은 전 태스크 동시 릴리스. "가장 어려운" 태스크셋은
각 태스크가 데드라인을 **간신히** 맞추도록 C_i를 극대화한 구성이다. 이 구성에서
이용률이 최소가 되도록 풀면, 태스크 주기들이 T_{i+1} = k·T_i (k는 정수)의
재귀 관계를 만족해야 함이 유도되고, 이를 정리하면 위 상한이 나온다.
전체 증명은 Liu & Layland(1973) 참조. ∎

> ⚠️ 이 상한은 **충분조건**이다. 상한을 넘어도 스케줄가능할 수 있으며,
> 그럴 때는 §3의 응답시간 분석(정밀 검사)으로 판정한다.

### 정리 4 — Bini 쌍곡선 상한 (Bini, Buttazzo, Buttazzo, 2003)

> **명제.** 다음이 성립하면 RMS로 스케줄가능하다.
>
> ```
> ∏ᵢ (Uᵢ + 1)  ≤  2
> ```

**설명.** ∏(1+U_i) ≥ 1 + ΣU_i 이므로, 이 조건은 Liu–Layland 상한보다
**항상 약하지 않다**(더 많은 태스크셋을 통과시킨다). 계산이 간단하고
LL 상한의 "낙관적 한계"를 보완하므로 실무에서 함께 사용한다.

## 3. 정밀 검증 — 응답시간 분석 (Response Time Analysis, RTA)

이용률 검사는 충분조건일 뿐이므로, **필요충분에 가까운 정밀 검사**가 필요하다.
Audsley 계열의 응답시간 분석을 유도한다.

### 3.1 방정식 유도

τ_i가 릴리스(임계 순간, t=0)된 뒤, 시각 t까지 τ_i를 방해한 고우선순위 작업량은

```
Wᵢ(t) = Σ_{j∈hp(i)} ⌈ t / T_j ⌉ · C_j
```

⌈·⌉는 올림(ceiling)으로, 구간 [0, t)에 릴리스된 τ_j 작업의 수가 ⌈t/T_j⌉개이기 때문이다.
τ_i의 작업은 **자신의 실행(C_i) + 차단(B_i) + 고우선순위 간섭(W_i)**이 모두 끝나는
가장 이른 시각에 완료된다. 즉

```
Rᵢ = Cᵢ + Bᵢ + Wᵢ(Rᵢ)          … ①
```

R_i는 함수 f(t) = C_i + B_i + W_i(t)의 **최소 고정점(least fixed point)**이다.

### 3.2 고정점 반복

①을 직접 풀 수 없으므로(우변에 R_i가 있음), 반복으로 푼다.

```
Rᵢ⁰ = Cᵢ
Rᵢ^(k+1) = Cᵢ + Bᵢ + Σ_{j∈hp(i)} ⌈ Rᵢ^k / T_j ⌉ · C_j      … ②
```

- f는 **단조비감소** 함수이므로 수열 {R_i^k}는 단조증가한다.
- R_i^k ≤ D_i 동안 수렴하면 그 값이 최악 응답시간이다. **R_i ≤ D_i ⟺ 스케줄가능**.
- 어느 단계에서 R_i^k > D_i가 되면 데드라인 위반 → **스케줄 불가능** (반복 종료).

### 3.3 차단시간 B_i와 우선순위 상속

뮤텍스 공유로 인한 **우선순위 역전**을 반영하는 항이 B_i이다.

- τ_i가 뮤텍스 M을 기다리는데, M을 **더 낮은 우선순위 태스크 τ_low**가 잡고 있다면
  τ_i는 τ_low가 임계구역을 놓을 때까지 차단된다.
- **우선순위 상속**이 있으면(FreeRTOS 뮤텍스 기본), τ_low는 일시적으로 τ_i의
  우선순위를 물려받아 **중간 우선순위 태스크들이 차단을 연장(연쇄 차단)하지 못한다.**
- 따라서 상속 하에서:

```
Bᵢ = max { τ_low가 공유 뮤텍스를 잡는 최장 임계구역 길이 }   (τ_low의 우선순위 < pᵢ)
```

> 💡 이것이 코드에서 액추에이터 보호에 **뮤텍스**(상속 제공)를 쓰고, 단순 바이너리
> 세마포어를 쓰지 않는 수학적 이유다.

## 4. 본 코드 태스크셋 모델링

`main_fixed.c`의 태스크를 위 모델로 매핑한다. WCET(C_i)는 **추정치**이며, 근거를
명시하고 §8에서 실측 후 재계산한다.

### 4.1 태스크 파라미터 (우선순위: 클수록 높음, FreeRTOS 규약)

| 태스크 | T_i | C_i (추정) | p_i | D_i | B_i | C_i 추정 근거 |
|---|---|---|---|---|---|---|
| Watchdog | 100 ms | 0.05 ms | 6 | **1000 ms** | 0 | 카운터 4개 비교 + IWDG refresh ≈ 수십 µs |
| CAN_Rx | 1 ms* | 0.04 ms | 5 | 1 ms | 0.05 ms | 수신 1건 처리(HAL+변환+큐) ≈ 수십 µs |
| Sensor | 10 ms | 0.80 ms | **4** | 10 ms | 0 | ADC 2회(~50µs) + **BMP280 I2C 3B 읽기(~0.7ms, 블로킹)** |
| Actuator | 20 ms | 0.05 ms | 3 | 20 ms | 0.01 ms | 큐 수신+뮤텍스+PWM/GPIO ≈ 수십 µs; 차단=펌웨어 임계구역 |
| Debug | 50 ms | 6.00 ms | 2 | 50 ms | 0 | **printf 블로킹**: JSON ~70B ÷ 11.52kB/s ≈ 6 ms |
| Firmware | 5000 ms | 0.10 ms | 1 | 5000 ms | 0 | 업데이트 플래그 확인뿐(업데이트 경로는 §7.2 별도) |

> \* CAN_Rx는 산발(sporadic) 태스크다. T_c = 1ms는 **"초당 최대 1000개 메시지"**라는
> 설계 상한을 뜻한다(500kbps 버스의 실효 최대 ~3800 msg/s의 약 26%). 이 상한은
> 요구사항으로 문서화되어야 하며, 초과 시 링 버퍼 유실이 발생한다.

> **우선순위 분리(2026-08-18 2차 수정)**: 기존에는 Sensor와 Actuator가 모두 p=3이었다.
> FreeRTOS는 동일 우선순위를 타임슬라이싱하므로 RTA의 "서로 다른 고정 우선순위" 가정과
> 어긋났다. Sensor(10ms)=4 > Actuator(20ms)=3으로 분리하여 RMS 순서와 RTA 가정을
> 동시에 만족시켰다. CAN_Rx의 B_i는 긴급정지 경로가 대기하는 액추에이터 뮤텍스의
> 최악 임계구역(우선순위 상속으로 유계)을 0.05ms 보수치로 반영했다.

### 4.2 C_i 추정의 근거 (왜 이 값인가)

- **Debug가 6ms로 가장 큼** — `printf`가 `HAL_UART_Transmit(..., HAL_MAX_DELAY)`의
  **블로킹 전송**이기 때문. 115200bps는 11.52kB/s이므로 70바이트 JSON 한 줄 ≈ 6.1ms.
  디버그 태스크 하나가 전체 이용률의 약 절반(12%)을 차지한다. → **측정 계획서의
  "printf ON/OFF 분리 측정"이 수학적으로도 정당화된다.**
- **Sensor가 두 번째로 큼** — BMP280 온도 읽기가 100kHz I2C에서 3바이트 트랜잭션
  (~60비트 왕복 ≈ 0.6~0.7ms)이라 폴링 방식에서는 블로킹이 지배적.
- 나머지는 레지스터/핀 조작 수준이라 µs 단위.

## 6. 우선순위 배정의 수학적 정당성

### 6.1 RMS 정합성 검토

RMS 순서(주기 오름차순 = 우선순위 내림차순)와 현재 코드를 비교한다.

| 순위 | RMS가 요구하는 태스크(주기) | 코드의 우선순위 | 일치? |
|---|---|---|---|
| 1 | CAN_Rx (1ms) | 5 | ✅ |
| 2 | Sensor (10ms) | 4 | ✅ |
| 3 | Actuator (20ms) | 3 | ✅ |
| 4 | Debug (50ms) | 2 | ✅ |
| 5 | **Watchdog (100ms)** | **6 (최상위)** | ❌ **예외** |
| 6 | Firmware (5000ms) | 1 | ✅ |

**예외는 워치독 단 하나.** (2026-08-18 수정 전에는 Sensor/Actuator가 동순위 p=3로
RMS와 "사실상 일치"였으나, RTA 가정(상이한 고정 우선순위)을 만족시키기 위해 분리했다.) 정리 2(RMS 최적성)가 요구하는 "D_i = T_i" 가정이
워치독에는 **성립하지 않으므로** 이 예외는 정리의 위반이 아니다. 구체적으로:

### 6.2 워치독 예외의 세 가지 정당화

1. **D ≠ T**: 워치독의 실제 데드라인은 IWDG 타임아웃 = **1000ms**이고 주기는 100ms.
   RMS 최적성 정리는 D = T를 전제하므로 워치독에는 적용 자체가 안 된다.
   D ≫ T인 태스크는 "주기가 긴데 데드라인이 더 길다"는 뜻이므로, RMS 순서보다
   낮아도 되고 높아도 되는 **자유도가 존재**한다.
2. **간섭이 무시 가능**: C_w = 0.05ms는 극소. 최상위 배치가 타 태스크에 주는
   간섭은 응답시간 +0.05ms 미만이다(§6.3 시나리오 B에서 정량 확인).
3. **안전 우선 원칙**: 워치독은 "고장 태스크 검출 지연"을 최소화하는 안전 모니터다.
   최상위 우선순위는 어떤 부하 상황에서도 100ms 주기 실행을 보장하므로,
   결함 검출 상한이 결정론적으로 유지된다.

### 6.3 민감도 분석 — 예외를 바꿔도 증명이 성립함을 확인

**시나리오 B — 엄격 RMS(전 태스크 주기순 재배정: CAN=6, Sensor=5, Actuator=4, Debug=3, Watchdog=2, Firmware=1):**

```
Watchdog    100.00    0.05       2   1000.00    7.2200    4    ✅
CAN_Rx        1.00    0.04       6      1.00    0.0900    2    ✅
Sensor       10.00    0.80       5     10.00    0.8400    2    ✅
Actuator     20.00    0.05       4     20.00    0.9000    2    ✅
Debug        50.00    6.00       3     50.00    7.1700    3    ✅
Firmware   5000.00    0.10       1   5000.00    7.3200    3    ✅
... 전 태스크 스케줄가능 ✅
```

→ 워치독을 RMS 위치로 내려도 **여전히 스케줄가능**하다. 즉 현재의 "안전 우선" 배정은
정당화 가능하고, 대안(RMS)도 가능하다. **둘 다 성립하므로 배정은 설계 선택이며,
현재 선택의 근거는 §6.2의 안전 우선 원칙이다.**

**시나리오 C — printf 비활성화(Debug C=6ms → 0.1ms):**

```
전체 이용률 U = 0.1250 (12.50%)   ← 24.3% → 12.5%로 반감
Firmware R    = 1.18ms            ← 7.32ms → 1.18ms로 6배 단축
```

→ 디버그 출력을 인터럽트/DMA 전송으로 바꾸면 전체 이용률이 절반으로 떨어진다.
이것이 실측 계획서에서 printf를 분리 측정하라고 한 이유의 정량적 근거다.

## 7. 특수 경로 분석

### 7.1 긴급정지(비주기 안전 경로)의 응답시간 상한

긴급정지는 주기 태스크가 아니므로, "메시지 수신 → PWM=0"의 **End-to-End 상한**을
구성 요소의 합으로 계산한다.

```
R_emg = (버스 전송) + (ISR 처리) + (스케줄링 지연) + (안전 적용)
      =  260 µs      +  40 µs     +  60 µs        +  20 µs
      ≈  0.4 ms
```

| 구간 | 상한 | 근거 |
|---|---|---|
| 버스 전송 | ~260 µs | 500kbps에서 8바이트 표준 프레임 ≈ 130bit × 2µs |
| ISR 처리 | ~40 µs | `HAL_CAN_GetRxMessage` + 링버퍼 저장 + 세마포어 give |
| 스케줄링 지연 | ~60 µs | CAN_Rx보다 높은 우선순위는 Watchdog뿐 → 최악 C_w(50µs) + 문맥전환 |
| 안전 적용 | ~20 µs | 뮤텍스 즉시 획득 + PWM/GPIO 쓰기 |

- 뮤텍스가 액추에이터에 잡혀 있어도 **우선순위 상속**으로 차단은 그 임계구역
  (~10µs) 한 번으로 제한된다 → 긴급 경로에 `portMAX_DELAY`를 쓴 근거.
- 최종 판정은 실측(로직 애널라이저, 최악값)으로 확정한다.

### 7.2 펌웨어 업데이트 — 모드 전환(Mode Change)

`vTaskSuspendAll()` 이후의 플래싱 구간은 **선점이 없는 비선점 구간**으로,
주기 태스크 분석 프레임워크의 **밖**에 있는 "모드 전환"이다.

- 진입 전에 스로틀/팬을 안전 상태로 만들므로, 이 구간에서 데드라인 위반의 결과는 없다.
- 유일한 실시간 제약은 **IWDG(1000ms)를 넘기지 않는 것**이며, 섹터 삭제 전·기록 중
  1KB마다 피드하여 보장한다(수정 1). 이 제약은 정량화하면:
  ```
  (섹터 1개 삭제 시간) < 1000ms,  (1KB 기록 시간) < 1000ms
  ```
  STM32F4의 16KB 섹터 삭제(~16–400ms)와 1KB 기록(~수 ms)은 모두 여유 있게 만족한다.

## 부록 A — 계산 스크립트 (rta_analysis.py)

동봉된 스크립트의 핵심 로직 (전체는 워크스페이스 `rta_analysis.py` 참조):

```python
def rta(task, tasks):
    name, T, C, p, D, B = task
    hp = [t for t in tasks if t[3] > p]      # 더 높은 우선순위 집합
    R = C                                     # R^0 = C
    while True:
        s = C + B
        for (_n, _T, _C, _p, _D, _B) in hp:
            s += math.ceil(R / _T) * _C       # Σ ⌈R/T_j⌉·C_j
        if abs(s - R) < 1e-9: return R        # 수렴
        if s > D: return s                    # 데드라인 위반
        R = s
```

실행 방법:

```bash
python3 rta_analysis.py
```
