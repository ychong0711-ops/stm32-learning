스테이징 부트로더 + FreeRTOS 애플리케이션 · 호스트 검증까지 끝난 코드를 실제 보드에서 확인하는 절차

0. 이 문서의 목적과 범위

이 저장소의 코드는 호스트에서 검증할 수 있는 것은 모두 검증된 상태입니다. 크로스컴파일 성공, 이미지 CRC 3자 일치, 벡터 테이블 정합성, 링커 메모리 배치, 정적 스택 분석까지 끝났습니다. 그러나 아래 항목들은 원리적으로 실물에서만 확인할 수 있습니다.

실물에서만 확인 가능한 3가지
  • 180MHz 오버드라이브 안정성 — PLL 락, 플래시 레이턴시, 전압 레귤레이터 전환은 실리콘·온도·전원 품질에 의존합니다.
  • IWDG 타임아웃 마진 — LSI는 공칭 32kHz지만 데이터시트 편차가 큽니다. 실제 섹터 삭제 시간과의 마진은 측정해야 압니다.
  • 부트로더 설치·복구 경로의 실동작 — 플래시 삭제 중 CPU 스톨, 백업 SRAM 유지, 앱 점프 후 벡터 재배치는 실행해 봐야 압니다.

이 가이드는 그 3가지를 포함해 총 8개 항목을 순서대로 확인하도록 구성했습니다. 각 항목마다 방법 합격 기준 실패 시 조치를 함께 적었습니다.

2. 핀맵과 배선

아래 핀 번호는 UM1724 (STM32 Nucleo-64 사용자 매뉴얼)의 ST Morpho 커넥터 기준입니다. Arduino 헤더(CN5~CN10 중 CN8/CN9)가 아니라 보드 바깥쪽 2열 헤더 CN7/CN10입니다.

4. 부트로더 검증 핵심

4.1 클록 180MHz 확인

오버드라이브 전환이 실제로 성공했는지 봅니다. 세 가지 방법 중 하나를 쓰십시오.

방법 A — UART 타임스탬프 (장비 불필요) 권장

Debug 태스크는 1초 주기로 출력합니다. 스톱워치로 60줄이 나오는 시간을 재십시오.

  • 60줄 ≈ 60초 → 틱 정상 → SYSCLK 정상
  • 60줄이 67초쯤 걸림 → 168MHz로 동작 중(오버드라이브 실패, 180/168 = 1.071)
  • 60줄이 7.5배 느림 → HSI 16MHz 폴백 (PLL 실패)

방법 B — GDB로 레지스터 직접 확인 정확

openocd -f interface/stlink.cfg -f target/stm32f4x.cfg &
arm-none-eabi-gdb build/app/app.elf
(gdb) target extended-remote :3333

# SystemCoreClock 변수 확인
(gdb) print/d SystemCoreClock
#  기대: 180000000

# PWR_CSR: ODRDY(bit16), ODSWRDY(bit17)이 모두 1이어야 오버드라이브 성공
(gdb) x/1xw 0x40007004
#  bit16·bit17이 모두 셋 → 0x00030000 마스크가 살아 있어야 함

# RCC_CFGR의 SWS[3:2] = 0b10 이면 시스템 클록 소스가 PLL
(gdb) x/1xw 0x40023808

방법 C — MCO 출력 후 스코프

PA8은 이 프로젝트에서 PWM에 쓰이므로, MCO2(PC9, CN10-1)를 SYSCLK/5로 설정해 36MHz를 관측하는 방식이 간섭이 없습니다.

실패 시 조치
system_stm32.c에서 HAL_PWREx_EnableOverDrive()가 HAL_RCC_OscConfig()와 HAL_RCC_ClockConfig() 사이에 있는지 확인하십시오. RM0390은 오버드라이브 전환 시 시스템 클록 소스가 HSI/HSE여야 한다고 규정합니다. 그래도 실패하면 168MHz(PLLN=336, VOS만 사용)로 낮춰 진행하십시오 — 이 프로젝트의 다른 검증에는 영향이 없습니다.

4.2 정상 부팅 경로

앱이 유효하고 설치 요청이 없을 때, 부트로더는 아무 표시 없이 즉시 앱으로 점프해야 합니다.

관찰의미
리셋 후 LED 점멸 없이 곧바로 JSON 출력정상 (부트로더가 조용히 통과)
LED가 100ms 간격 2회 점멸 후 진행설치를 시작했음 → 이전 스테이징이 남아 있음
LED가 계속 빠르게 점멸, JSON 없음앱 무효 → 복구 대기 루프. §8 참조

부트 제어 블록 직접 읽기

백업 SRAM(0x40024000)에 부트로더의 판단 결과가 남습니다. GDB로 6워드를 읽으십시오.

(gdb) x/6xw 0x40024000
0x40024000: 0x5555aaaa  0x00000000  0x00000000  0x0000c7c7
0x40024010: 0x00000007  0xXXXXXXXX
#            ulMagic     ulRequest   ulAttempts  ulLastResult
#            ulResetCount            ulCheck
필드해석
ulMagic0x5555AAAA여야 블록이 유효
ulRequest0 = 요청 없음 / 0x55504454 = 설치 요청
ulAttempts설치 시도 횟수. 3에 도달하면 더 시도하지 않음
ulLastResult0xA5A5 설치됨 / 0xB6B6 복구됨 / 0xC7C7 유지 / 0xDEAD 실패
ulResetCount부트로더를 통과한 누적 부팅 횟수
전원을 끊으면 사라집니다
백업 SRAM은 VBAT가 유지될 때만 보존됩니다. VBAT에 배터리를 달지 않은 기본 Nucleo에서는 USB를 뽑으면 초기화됩니다. 리셋 버튼(NRST)으로만 재부팅하면 값이 유지됩니다. 이 차이 자체가 §4.3에서 관찰 대상입니다.

4.3 정상 이미지 설치 최우선

정상 경로는 "앱이 CAN으로 이미지를 수신 → 스테이징 기록"이지만, 전송 프로토콜은 아직 구현 전입니다. 전송 계층을 건너뛰고 디버거로 스테이징 영역에 이미지를 직접 써 넣으면, 그 이후의 검증·설치·점프 경로는 실제와 완전히 동일하게 동작합니다.

1단계 — 구별 가능한 새 버전 만들기

설치 성공을 눈으로 확인하려면 새 이미지가 이전과 달라야 합니다. Debug 출력 문자열을 바꾸는 것이 가장 확실합니다.

# main_fixed.c 의 Debug 태스크 출력에 표식을 하나 넣습니다. 예:
#   {"ts":%lu,... }  →  {"v":2,"ts":%lu,... }

make clean && make FW_VERSION=0x00020000
#  → build/app/app_image.bin 이 버전 2로 다시 생성됩니다

2단계 — 스테이징 배치로 재구성

이미지 파일을 그대로 0x08020000에 구우면 안 됩니다. 스테이징 영역은 앞 512B가 메타데이터이고 본문은 +0x200에서 시작합니다. tools/make_stage_blob.py가 이 배치를 맞춰 줍니다.

python3 tools/make_stage_blob.py \
        -i build/app/app_image.bin \
        -o build/stage.bin

스테이징 블롭 생성: build/stage.bin
  기록 주소   : 0x08020000 (섹터 5)
  블롭 크기   : 28752 B (메타 512 B + 본문 28240 B)
  헤더 매직   : 0x4D465733
  본문 CRC32  : 0xDD324005 (헤더 기록값)
  설치 표식   : 0xFFFFFFFF (소거 상태 — 정상)
설치 표식이 0xFFFFFFFF여야 합니다
+0x100에 0x494E5354('INST')가 찍혀 있으면 부트로더는 "이미 설치된 이미지"로 보고 건너뜁니다. 스크립트가 이 자리를 소거 상태로 남겨 줍니다.

3단계 — 스테이징에 기록하고 설치 요청

# 스테이징 영역에 이미지 주입
st-flash --reset write build/stage.bin 0x08020000

이제 부트로더에게 설치를 시켜야 합니다. 두 가지 방법이 있습니다.

  • 방법 A (자연스러움) — 앱의 펌웨어 태스크가 Bootloader_RequestInstallAndReset()을 호출하도록 트리거합니다. 이 함수는 전체 CRC를 재검증한 뒤 요청을 기록하고 시스템 리셋을 겁니다.
  • 방법 B (직접 주입) — GDB로 부트 제어 블록에 요청을 써 넣습니다. 체크섬까지 맞춰야 하므로 아래 순서를 따르십시오.
# 방법 B: 요청 워드를 쓰고 체크섬을 무효화 → 부트로더가 블록을 재초기화하지 않도록
# 하려면 체크섬 계산이 필요하므로, 더 간단한 우회를 씁니다:
#
#   앱 영역을 지우면 부트로더가 "앱 무효 + 스테이징 유효" 조건으로
#   요청 없이도 자동 설치합니다 (§4.5와 동일 경로).
#
# 즉 방법 B는 §4.5 자동 복구 시험으로 대체하는 것이 확실합니다.

4단계 — 관찰

4.4 손상 이미지 거부

CRC 검증이 실제로 동작하는지 봅니다. 이 시험은 안전 논거의 핵심입니다 — 깨진 이미지를 설치해 버리면 필드에서 벽돌이 됩니다.

시험 1 — 본문 손상 (CRC 불일치)

python3 tools/make_stage_blob.py \
        -i build/app/app_image.bin \
        -o build/stage_bad.bin --corrupt

#   고장 주입 : 본문 +0x40: 0x91 → 0x6E (CRC 불일치 유도)

st-flash --reset write build/stage_bad.bin 0x08020000

시험 2 — 헤더 매직 파손

python3 tools/make_stage_blob.py \
        -i build/app/app_image.bin \
        -o build/stage_nomagic.bin --break-magic

st-flash --reset write build/stage_nomagic.bin 0x08020000

이 블롭들은 호스트에서 이미 검증 함수에 통과시켜 결과를 확인했습니다. 실물에서도 동일해야 합니다.

블롭CheckHeaderVerify부트로더 기대 동작

stage_bad.binOKERR_IMG_CRC헤더는 통과하나 복사 후 검증에서 거부
stage_nomagic.binERR_MAGICERR_MAGIC헤더 단계에서 즉시 거부, 설치 시도조차 안 함

두 경우 모두 기존 앱이 그대로 계속 실행되어야 합니다(UART에 이전 버전 출력 유지). 특히 stage_nomagic.bin은 LED 점멸조차 없어야 합니다 — 설치를 시작하지 않기 때문입니다.
불합격이라면

4.5 앱 파손 자동 복구 최우선

앱이 죽어도 스테이징에 유효한 이미지가 있으면 부트로더가 요청 없이 자동으로 복구해야 합니다. 이것이 스테이징 패턴을 도입한 근본 이유입니다.

  1. 정상 이미지를 스테이징에 넣습니다. 
    python3 tools/make_stage_blob.py -i build/app/app_image.bin -o build/stage.bin
st-flash write build/stage.bin 0x08020000
  2. 앱 영역의 첫 섹터(섹터 1, 0x08004000)를 지워 앱을 고의로 파손합니다. 
    st-flash erase 0x08004000 0x4000
#  또는 OpenOCD:
#  flash erase_sector 0 1 1
  3. 리셋 버튼(검은색, B2)을 누릅니다.
합격 기준
  • LED 2회 점멸(설치 시작) → 소등(복사) → 3회 점멸(성공)
  • UART에 JSON 출력이 되살아남
  • ulLastResult == 0xB6B6 (BOOT_RESULT_RECOVERED)
사람이 개입하지 않고 벽돌 상태에서 스스로 살아났다면, 이 프로젝트에서 가장 설득력 있는 증빙입니다. 이 순간을 영상으로 남기는 것을 강력히 권합니다.

재시도 한계 확인 (선택)

스테이징도 깨져 있으면 무한 재시도에 빠지지 않아야 합니다.

# 앱도 지우고 스테이징도 깨진 이미지로 채웁니다
st-flash write build/stage_bad.bin 0x08020000
st-flash erase 0x08004000 0x4000
# 리셋 3회 반복

기대: ulAttempts가 1→2→3으로 증가하다 3에서 멈추고 ulLastResult == 0xDEAD가 되며, LED가 빠르게 계속 점멸하는 복구 대기 루프에 들어갑니다. 이 상태에서도 워치독은 계속 피드되므로 리셋 루프에 빠지지 않아야 합니다.

5. 실시간 성능 측정

이 절의 합격 기준은 docs/docs_measurement_plan.md에 정의된 값을 그대로 씁니다. 정적 분석으로 예측한 값과 실측값의 차이를 기록하는 것이 목적입니다 — 차이가 있다면 그 이유를 설명할 수 있어야 합니다.

5.1 스택 사용량 여유 ≥30%

FreeRTOS의 하이워터마크는 실행 중 실제로 도달한 최대 깊이를 알려 줍니다. 정적 분석값(.su 파일 기반)과 비교하십시오.

// Debug 태스크에 임시로 추가
UBaseType_t uxHW = uxTaskGetStackHighWaterMark(NULL);
printf("{\"task\":\"debug\",\"free_words\":%lu}\r\n", (unsigned long)uxHW);

또는 GDB에서 전체 태스크를 한 번에 봅니다.

(gdb) monitor reset halt
(gdb) continue
#  30초 이상 동작시킨 뒤 Ctrl+C
(gdb) info threads          # FreeRTOS 인식 시
(gdb) print uxTaskGetStackHighWaterMark(0)
태스크할당(워드)정적 예측실측 하이워터마크
Watchdog128–기록
CAN256–기록
Sensor128–기록
Actuator128136 B / 512 B기록
Debug256–기록
Firmware512–기록
하이워터마크가 예측보다 크다면
printf 계열이 스택을 많이 씁니다. 정적 분석(.su)은 재귀와 함수 포인터 경로를 못 잡습니다. 실측이 더 신뢰할 수 있는 값이며, 차이 자체를 보고서에 쓰는 것이 정직한 서술입니다.

5.2 주기 지터 ±100µs

10ms 주기 태스크의 실제 주기 편차를 봅니다. 가장 정확한 방법은 GPIO 토글 + 스코프입니다.

// 10ms 주기 태스크 루프 맨 앞에 추가
HAL_GPIO_TogglePin(GPIOB, GPIO_PIN_13);   // PB13 = CN10-30
  • 스코프를 PB13에 물리고 주기 측정 + 통계 기능을 켭니다.
  • 최소 1분간 관측하여 주기 최소·최대·표준편차를 기록합니다.
  • 토글이므로 반주기가 10ms입니다(전체 주기 20ms). 판정 시 주의하십시오.

스코프가 없으면 DWT 사이클 카운터로 대체합니다.

// DWT 활성화 (main 초기화 시 1회)
CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;
DWT->CYCCNT = 0;
DWT->CTRL  |= DWT_CTRL_CYCCNTENA_Msk;

// 주기 태스크 안에서
static uint32_t ulPrev = 0;
uint32_t ulNow = DWT->CYCCNT;
uint32_t ulDelta = ulNow - ulPrev;   // 180MHz에서 1 tick = 5.56ns
ulPrev = ulNow;
// 10ms = 1,800,000 사이클. ±100µs = ±18,000 사이클

5.3 CPU 사용률 평균 ≤70% / 피크 ≤85%

가장 간단하고 왜곡이 적은 방법은 유휴 훅에서 GPIO를 토글하고 듀티비를 재는 것입니다.

// app_hooks.c 의 vApplicationIdleHook()
void vApplicationIdleHook(void)
{
    HAL_GPIO_TogglePin(GPIOB, GPIO_PIN_13);
}

스코프로 PB13의 하이 듀티비를 재면 그것이 유휴 비율입니다. CPU 사용률 = 100% − 유휴 비율.

또는 FreeRTOS 런타임 통계를 켭니다.

// FreeRTOSConfig.h
#define configGENERATE_RUN_TIME_STATS   1
#define configUSE_TRACE_FACILITY        1
#define configUSE_STATS_FORMATTING_FUNCTIONS 1
// → vTaskGetRunTimeStats(buf) 로 태스크별 점유율 출력
부하 조건을 명시하십시오
아무 입력이 없는 상태의 CPU 사용률은 의미가 약합니다. CAN 프레임을 최대 속도로 주입한 상태에서의 피크값을 함께 기록해야 설계 여유를 증명할 수 있습니다.

5.4 긴급정지 E2E 지연 ≤10ms

CAN 버스에 긴급정지 프레임(ID 0x123)이 뜬 순간부터 FAN 출력(PB13)이 꺼질 때까지를 잽니다.

채널프로브 지점트리거
CH1CAN RX (PB8, CN10-3)하강 에지 (프레임 시작)
CH2FAN 출력 (PB13, CN10-30)액추에이터 차단
# USB-CAN 어댑터로 긴급정지 프레임 주입 (SocketCAN 예)
sudo ip link set can0 up type can bitrate 500000

CAN ID 참조 — 긴급정지 0x123, 스로틀 0x200, 팬 0x201.

10ms를 넘는다면

6. 워치독과 고장 주입 핵심

6.1 IWDG 설정값의 의미

bsp_iwdg.c의 IWDG_Init(ms)는 LSI를 32kHz로 가정하고 분주비를 4부터 256까지 올리며 reload = 32 × ms / div가 12비트에 들어가는 첫 조합을 씁니다.

(최악·빠름)		LSI 17kHz
(최악·느림)
1000 ms840001.00 s0.68 s1.88 s

여기가 이 프로젝트의 가장 취약한 가정입니다
LSI 편차를 최악(47kHz)으로 잡으면 앱의 워치독은 실제로 2.72초에 물립니다. 128KB 섹터 삭제가 약 2초 걸린다는 보고가 있으므로 마진은 0.72초에 불과합니다. §6.2에서 실제 LSI 주파수와 실제 삭제 시간을 반드시 측정하십시오.

6.2 LSI 실주파수와 플래시 삭제 시간 측정

LSI 실주파수 (TIM5 채널4 입력 캡처)

STM32F4는 LSI를 TIM5 채널4에 내부적으로 연결할 수 있습니다(RM0390 §6.2.11). 외부 배선이 필요 없습니다.

// TIM5_CH4를 입력 캡처로 설정하고 TIM_TIM5_LSI 소스를 선택
HAL_TIMEx_RemapConfig(&htim5, TIM_TIM5_LSI);
HAL_TIM_IC_Start_IT(&htim5, TIM_CHANNEL_4);

// 캡처 콜백에서 두 에지 간격으로 주파수 계산
// LSI_freq = TIM5 클록(APB1 타이머 클록) / (capture2 - capture1)

측정된 LSI 주파수를 기록지에 적으십시오. 실제 IWDG 타임아웃 = reload × div ÷ LSI_실측입니다.

플래시 섹터 삭제 시간

Flash_SetProgressHook()은 삭제 직전과 직후에 호출됩니다. 이 두 시점 사이가 곧 삭제 시간입니다.

// 훅에서 GPIO를 토글하면 스코프로 폭을 그대로 잴 수 있습니다
static void prvMeasureHook(void)
{
    HAL_GPIO_TogglePin(GPIOB, GPIO_PIN_13);   // PB13 = CN10-30
}
Flash_SetProgressHook(prvMeasureHook);

// 또는 DWT 사이클 카운터로:
// 훅 첫 호출에 시작값 저장, 두 번째 호출에 차이 계산 → UART 출력
섹터크기예상 삭제 시간실측
섹터 1~3 (앱)16 KB수백 ms기록
섹터 4 (앱)64 KB~1 s기록
섹터 5 (스테이징)128 KB~2 s기록
합격 기준
최장 삭제 시간 × 1.5 < (reload × div ÷ LSI_실측)
예: 삭제 2.1초 실측, LSI 실측 34kHz → 실제 타임아웃 = 4000×32÷34000 = 3.76초. 2.1 × 1.5 = 3.15초 < 3.76초 → 통과.
마진이 부족하다면 (권장 조치 순서)
  1. IWDG 타임아웃을 늘립니다. main_fixed.c의 IWDG_Init(4000U)를 6000~8000으로. 단, 워치독의 고장 검출 지연이 그만큼 늘어난다는 점을 문서에 남기십시오.
  2. 삭제를 분할합니다. 128KB 섹터 하나 대신 작은 섹터 여러 개로 스테이징을 재배치하면 훅 호출 간격이 짧아집니다.
  3. 앱에서는 삭제하지 않습니다. 삭제를 전부 부트로더(타임아웃 8초)로 옮기는 것이 근본 해법입니다.

6.3 워치독 고장 주입 최우선

워치독 태스크는 4개의 하트비트(CAN·Sensor·Actuator·Debug)가 모두 갱신되었을 때만 IWDG를 피드합니다. 따라서 태스크 하나만 멈춰도 리셋이 걸려야 합니다. 이것이 "워치독이 실제로 일하고 있다"는 증거입니다.

주입 방법 — 태스크 하나를 무한 루프에 빠뜨립니다

// 예: Sensor 태스크에 트리거를 심습니다.
// 특정 CAN 프레임을 받거나, 버튼(B1, PC13)을 누르면 걸리게 합니다.
if (xInjectFault != pdFALSE)
{
    for (;;) { }        // 하트비트 갱신이 멈춤
}

또는 디버거로 더 간단히 주입할 수 있습니다.

(gdb) continue
#  Ctrl+C 로 정지 후, Sensor 태스크만 영원히 대기시키기:
(gdb) print xInjectFault = 1
(gdb) continue

리셋 원인 확인

리셋이 걸린 뒤, 그것이 워치독에 의한 것임을 증명해야 합니다. 앱은 부팅 시 RCC->CSR의 상위 플래그를 ulResetCause에 보존합니다.

(gdb) print/x ulResetCause
#  bit 29 (0x20000000) = IWDGRSTF  → 독립 워치독 리셋  ← 이것이 목표
#  bit 30 (0x40000000) = WWDGRSTF  → 윈도우 워치독
#  bit 28 (0x10000000) = SFTRSTF   → 소프트웨어 리셋
#  bit 26 (0x04000000) = PORRSTF   → 파워온 리셋
#  bit 25 (0x02000000) = PINRSTF   → NRST 핀 리셋

UART로 바로 찍어 두면 디버거 없이도 확인됩니다.

printf("{\"reset_cause\":\"0x%08lX\",\"iwdg\":%d}\r\n",
       (unsigned long)ulResetCause,
       (ulResetCause & 0x20000000U) ? 1 : 0);
합격 기준
  • 고장 주입 후 약 4초 이내(= IWDG 타임아웃)에 보드가 리셋됩니다.
  • 재부팅 후 ulResetCause의 bit 29(IWDGRSTF)가 1입니다.
  • 주입을 해제하면 정상 동작으로 복귀합니다.
펌웨어 갱신 중에는 리셋되지 않아야 합니다
xFirmwareUpdateActive가 참이면 워치독 태스크는 하트비트와 무관하게 무조건 피드합니다. 갱신 중 다른 태스크가 지연되어도 리셋되지 않는 것이 의도된 동작입니다. 이 조건도 함께 시험하십시오 — 갱신 중 고장 주입 시 리셋이 걸리지 않아야 합니다.

8. 문제 해결

8.1 증상별 진단

아무 반응이 없다 (LED도 UART도 없음)
  • st-info --probe로 보드가 인식되는지 먼저 확인합니다.
  • 결합 이미지를 다시 굽습니다: make flash-combined
  • 부트로더가 지워졌을 가능성 — 앱만 0x08000000에 구운 실수가 가장 흔합니다.
  • 완전 초기화: st-flash erase 후 make flash-combined
LED가 계속 빠르게 점멸하고 UART 출력이 없다
부트로더의 복구 대기 루프입니다. 앱도 무효이고 설치 가능한 스테이징 이미지도 없다는 뜻입니다. 이것은 고장이 아니라 설계된 안전 동작입니다. 
make flash-app          # 앱을 다시 굽습니다
# 또는 스테이징에 정상 이미지를 넣고 리셋 (자동 복구 경로 확인)
UART에 깨진 문자가 나온다
  • 터미널 보레이트가 115200인지 확인합니다.
  • 클록이 180MHz가 아니면 UART 분주가 틀어져 전부 깨집니다 → §4.1을 먼저 수행하십시오. 깨진 문자는 클록 실패의 신호인 경우가 많습니다.
부팅 직후 하드폴트로 보인다
벡터 테이블 오프셋 문제일 가능성이 높습니다. 앱은 반드시 아래 정의로 빌드되어야 합니다. 
-DUSER_VECT_TAB_ADDRESS -DVECT_TAB_OFFSET=0x4000
이 정의가 빠지면 SCB->VTOR이 0x08000000을 가리켜 첫 인터럽트에서 부트로더의 벡터로 점프합니다. make clean && make로 다시 빌드하십시오.
설치가 시작되지 않는다 (LED 2회 점멸 없음)
부트로더가 스테이징 헤더를 무효로 판단한 것입니다. 순서대로 확인하십시오. 
# 1. 스테이징 영역 앞부분을 직접 덤프
(gdb) x/8xw 0x08020000
#    첫 워드가 0x4D465733(매직)이어야 합니다

# 2. 설치 표식이 이미 찍혀 있지 않은지 확인
(gdb) x/1xw 0x08020100
#    0x494E5354('INST')이면 이미 설치된 것으로 간주됩니다 → 섹터 5를 지우고 다시 주입

# 3. 시도 횟수가 한계에 걸리지 않았는지
(gdb) x/6xw 0x40024000
#    ulAttempts가 3이면 더 시도하지 않습니다
설치 도중 리셋이 반복된다
워치독 마진 부족이 유력합니다. §6.2를 수행해 실제 삭제 시간과 LSI 주파수를 측정하고, 필요하면 IWDG 타임아웃을 늘리십시오. 이것이 이 프로젝트에서 가장 예상되는 실패 모드입니다.
백업 SRAM 값이 매번 0으로 초기화된다
VBAT에 백업 전원이 없으면 USB를 뽑을 때 내용이 사라집니다. 정상입니다. 값을 유지하려면 NRST 버튼으로만 재부팅하거나 VBAT에 코인셀을 연결하십시오.

8.2 완전 초기화 절차

상태가 꼬여서 무엇이 문제인지 모르겠을 때 쓰는 최후 수단입니다.

# 1. 플래시 전체 소거 (부트로더·앱·스테이징 모두)
st-flash erase

# 3. 재빌드 후 결합 이미지 플래싱
cd 02_source_code
make clean && make
make flash-combined
