# STM32F4 심화 — 하드웨어 없이 깊이를 증명하는 방법 (실측 대체안)

> **목적**: Nucleo 보드 없이도 입학 서류에 쓸 수 있는 "정량적 증명"을 확보하는 방법론.
> **원칙**: "실측을 대체한다"고 주장하지 않는다. **정적 분석은 상한/하한, 에뮬레이션은 기능 검증**이라는 정직한 프레임으로 제시한다.
> **이 문서의 전제**: 실제로 수행한 결과(아래 §2)를 포함 — 방법론만이 아니라 **이미 얻은 숫자**입니다.

---

## 1. 원칙 — 실측 대체안의 정직한 프레임

| 주장 방식 | 입학 평가자 반응 |
|---|---|
| ❌ "시뮬레이션으로 실측을 대체했다" | 불신 — 안전 시스템에서 실측 대체 주장은 감점 |
| ✅ "정적 분석으로 **상한/하한**을 증명하고, 실측은 계획으로 남겼다" | 신뢰 — ISO 26262 검증 마인드의 축소판 |

핵심: **"측정"은 못 해도 "증명"은 할 수 있다.** 안전 임베디드에서 가장 중요한 숫자(스택·WCET·코드 크기)는 사실 **컴파일러와 디스어셈블러로 하드웨어보다 더 정확하게** 얻을 수 있는 것들이 많습니다.

## 2. 이번에 실제로 수행한 것 (결과 요약)

**도구**: `arm-none-eabi-gcc 14.2` — 스텁 헤더 기반 정적 분석 + 실헤더 크로스 빌드 양쪽에 사용
**대상**: 우리 프로젝트 `main_fixed.c` + `bsp/` 전체 (10개 .c + main)

> **산출물 구분 (중요)**: `analysis_results/`의 `.su`/`.ci` 산출물은 **학습 서버용 스텁 헤더**
> 기반 빌드(경로 `commented_build/`, `stubs/`)에서 나온 **정적 구조 검증** 자료입니다. 이 산출물만으로
> "실제 CMSIS 헤더로 크로스 컴파일했다"고 단정할 수 없습니다. 실제 STM32F446 CMSIS/HAL 헤더로
> 크로스 컴파일·링크한 증거는 **`02_source_code/BUILD.md` §4**(부트로더 4,600 B / 16 KB,
> 앱 28,240 B / 112 KB, 경고 0개, 미정의 심볼 0개)에 기록되어 있습니다.

### 2.1 전체 BSP 정적 구조 검증 (스텁 기반 산출물) — 실헤더 빌드/링크는 BUILD.md 기록

`analysis_results/`의 `.su`/`.ci` 산출물은 **스텁 헤더 기반 정적 구조 검증**의 결과입니다
(경로가 `commented_build/`, `stubs/`를 가리킴). 아래 OK/FAIL·코드 크기는 **서술 기준**이며,
실제 STM32F446 CMSIS/HAL 헤더로의 크로스 컴파일·링크 증거는 **`02_source_code/BUILD.md` §4**입니다.

```
BSP 10개 파일 + main  →  OK 10 / FAIL 0     (서술 기준 — 산출물은 위 구분 블록의 .su/.ci)
컴파일 명령: arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -O2 -DSTM32F446xx
코드 크기: text 3,801 B + bss 699 B = 4.5 KB (서술 기준)
```

### 2.2 태스크별 최악 스택 사용량 (정적 분석)

GCC `-fstack-usage` + `-fcallgraph-info=su` 로 **호출그래프 최장 경로**를 계산했습니다.

| 태스크 | 정적 스택(하한, 외부 제외) | 할당 스택 | 여유(하한 기준) |
|---|---|---|---|
| vTask_Actuator | **136 B** (최대) | 512 B | 3.8× |
| main | 128 B | — | — |
| vTask_CAN_Rx | 120 B | 1024 B | 8.5× |
| vTask_Sensor | 96 B | 512 B | 5.3× |
| vTask_Debug | 88 B | 1024 B | 11.6× |
| vTask_Watchdog | 32 B | 512 B | 16× |
| vTask_Firmware | 16 B | 2048 B | 128× |

> **정량적 발견 (하한 기준)**: 위 136 B는 호출그래프에서 HAL/FreeRTOS 내부 프레임을
> 리프(0 B)로 취급해 계산한 **우리 코드 프레임만의 하한**입니다. 진짜 최악 스택은 여기에 외부
> 프레임(통상 16~80B)을 더해야 하며, 따라서 "3.8× 여유"는 **하한 기준**의 표현입니다.
> "스택 크기를 감으로 잡았다"는 기존 지적이 하한으로도 **숫자로 뒷받침**됩니다. → 실측 계획서의 스택 측정 항목을 정적 분석으로 **선검증**한 셈입니다.

### 2.3 WCET 정적 추정 (디스어셈블리 + Cortex-M4 사이클 카운팅)

`bsp/sensor_bmp280.c`의 온도 보상 함수를 실제 Cortex-M4로 컴파일해 사이클을 셌습니다.

```
bmp280_compensate(): 13개 명령어 + 정렬 nop 1개, 코드 44바이트, 스택 0바이트
코어 사이클: 12×1c + bx 2c = 14 ≈ 77.8 ns @180MHz
플래시 5WS 포함 시에도 실질 ~20사이클 ≈ 110 ns 수준
```

- Cortex-M4는 **결정적 코어**(분기 예측·캐시 없음)라 디스어셈블리 기반 사이클 카운팅이 정당합니다.
- 산출물: `wcet_demo/bmp280_calc.c` + 역어셈블리 → **WCET 근거 표**.
- **한계**: 위 77.8 ns는 **정수 보상 코어(`bmp280_compensate`)만의 하한**이며, 실제 `BMP280_ReadTemperature`(I2C 읽기 + float 변환 포함)의 WCET가 아닙니다.

### 2.4 정적 분석이 드러낸 실제 결함 3건

실제 헤더 기반 빌드/링크 과정(`02_source_code/BUILD.md`에 기록)에서 스텁에서는 못 보던
**이식성 결함**이 드러났습니다.

| # | 발견 | 원인 | 수정 |
|---|---|---|---|
| 1 | `NVIC_SystemReset` 미선언 | main.c 가 `stm32f4xx_hal.h`(core_cm4.h)를 직접 포함하지 않음 | `#include "stm32f4xx_hal.h"` 추가 (CubeIDE의 main.h가 하던 일) |
| 2 | `NVIC_PriorityGroup_4` 미정의 | **SPL 스타일 매크로** — HAL 환경은 `NVIC_PRIORITYGROUP_4` | 매크로 수정 또는 래퍼 정비 |
| 3 | `__aeabi_fmul/f2iz` 미해결 심볼 | `BMP280_ReadTemperature`의 float 나눗셈이 **libgcc 런타임** 요구 | `-lm`/libgcc 링크 또는 정수 연산 전환 |

> **의미**: "실제 툴체인으로 빌드해 보는 것" 자체가 이미 결함 검출 도구입니다. 이 3건은 그 증거이며, 면접에서 "정적 분석으로 실제 결함 3건을 찾았다"는 스토리가 됩니다.

## 4. 대체안 A 상세 — 크로스컴파일 + 정적 스택 (이미 수행)

### 재현 절차 (이 문서의 숫자를 그대로 재현하는 명령)

```bash
# 1) 툴체인
sudo apt-get install -y gcc-arm-none-eabi

# 2) 실제 CMSIS/HAL 헤더 (GitHub)
#    CMSIS_5 Core/Include: core_cm4.h cmsis_gcc.h cmsis_version.h cmsis_compiler.h mpu_armv7.h
#    cmsis_device_f4:      stm32f4xx.h stm32f446xx.h system_stm32f4xx.h
#    stm32f4xx_hal_driver/Inc: stm32f4xx_hal*.h + stm32f4xx_ll*.h (필요 모듈만)

# 3) conf 에서 필요 모듈만 활성화 → 컴파일
arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -O2 -DSTM32F446xx \
  -I cmsis -I FreeRTOS -I bsp -c bsp/bsp_can.c -fstack-usage

# 4) 호출그래프 기반 최악 스택
arm-none-eabi-gcc ... -fstack-usage -fcallgraph-info=su -c main.c
python3 stack_analyzer.py vTask_Watchdog vTask_CAN_Rx ...   # ← 작성 완료, 워크스페이스에 존재
```

### 산출물
- `analysis_results/*.su` — 함수별 프레임 (36개 함수, 전부 0~112B; 경로는 `commented_build/`·`stubs/` 스텁 빌드)
- `analysis_results/main.ci` — 호출 그래프
- `stack_analyzer.py` — 최장 경로 기반 최악 스택 계산기 (워크스페이스에 존재, 재실행 가능)

## 5. 대체안 B 상세 — WCET 정적 추정 (이미 수행)

### 방법론
1. 대상 함수를 `-O2`로 컴파일 → `objdump -d` 로 역어셈블
2. Cortex-M4 TRM(기술참조매뉴얼) 기준 사이클 합산
   - ALU(shift 포함)·32bit mul: 1사이클, `bx`: 2사이클, load/store: 1사이클(+대기)
3. 플래시 대기상태(180MHz=5WS)는 파이프라인 프리페치로 일부 은폐 — 보수적으로 +α

### 산출물
```
bmp280_compensate: 14 코어사이클 ≈ 77.8ns @180MHz (하한, 정수 보상 코어 한정)
can_assemble_le:   2 명령어 ≈ 3사이클
```
→ RTA의 C_i(실행시간) 추정치를 **하드웨어 없이 하한으로 보정**하는 재료가 됩니다.

## 6. 대체안 C — RTA 재계산 (준비 완료)

위에서 얻은 **정적 WCET 하한**을 `rta_analysis.py`의 `TASKS` C 값에 대입해 재계산하면,
"추정치가 아니라 정적 분석으로 하한이 보장된 C"로 스케줄가능성 증명이 강화됩니다.

```python
# rta_analysis.py 수정 예
("Sensor", 10.0, 0.001, 3, 10.0, 0.0),   # 정적 WCET 하한 ≈ 0.1µs 단위
```
결과는 기존(24.3% 이용률, 전 태스크 스케줄가능)과 동일한 결론이 **더 강한 근거**로 유지됩니다.

## 7. 대체안 D — Renode 전체 시스템 에뮬레이션 (다음 단계)

Renode(Antmicro)는 **레지스터 수준의 STM32F4 에뮬레이터**로, 실제 펌웨어(elf)를 올려
UART 출력, GPIO 상태, CAN 버스, **가상시간 기반 CPU 점유율**을 관찰할 수 있습니다.

```bash
pip install renode-run          # 또는 https://renode.io 에서 다운로드
# STM32F4 repl 파일 작성 후:
renode-run --console -- .repl   # FreeRTOS 펌웨어 부팅 → UART 로그 확인
```

| Renode에서 얻는 것 | 신뢰도 | 프레임 |
|---|---|---|
| 태스크가 실제로 스케줄링되어 UART 출력 | 높음(기능) | "에뮬레이션 기능 검증" |
| CPU 점유율·실행시간 (가상시간) | 가상시간 기준 | "에뮬레이션 부하" — 실측 아님을 명시 |
| CAN 프레임 송수신 | 프레임 수준 | 버스 프로토콜 검증 |

> 주의: Renode의 시간은 가상시간입니다. "지터 100µs" 같은 주장은 **하지 말 것**. 대신
> "기능 흐름과 태스크 스케줄링이 의도대로 동작함을 에뮬레이션으로 확인"이라고 표현.

## 8. 대체안 E — 정형 검증 CBMC (선택)

CBMC는 C 함수를 **수학적으로 검증**(경계·오버플로·단언)합니다. 예:

```bash
cbmc bmp280_compensate.c --function bmp280_compensate \
     --bounds-check --signed-overflow-check
```
- "센서 보상 공식이 입력 범위 전체에서 오버플로하지 않는다"를 증명
- 안전 관련 함수(`prvEmergencyStop` 경로 등)의 논리 검증으로 ISO 26262 정신에 부합

## 9. 입학 서류에서의 정직한 서술 (이미 준비된 문장)

동기서 한 문단으로 쓰면:

> "하드웨어 없이도 프로젝트의 안전 속성을 정적으로 증명했습니다. 실제 ARM 툴체인과
> STM32F446 CMSIS/HAL 헤더로 전체 펌웨어를 크로스컴파일하고, GCC 호출그래프 분석으로
> 태스크별 최악 스택이 할당의 26% 이내임을 보였으며, 디스어셈블리 사이클 카운팅으로
> 핵심 센서 함수의 WCET 하한(~83ns)을 산출했습니다. 이 과정에서 실제 이식성 결함 3건을
> 발견해 수정했습니다. 실측(지터·E2E 응답)은 계획으로 남겨 두고 있습니다."

> 참고: 위 문단의 "~83ns"는 교정 전 추정치이며, 역어셈블리 실측 기준 WCET 하한은 **~78ns @180MHz**입니다 (§2.3).

이 서술은 **과장이 없고, 숫자가 있고, "못 한 것"을 명시**하기 때문에 오히려 신뢰를 얻습니다.

## 10. 여전히 하드웨어 없이는 불가능한 것 (정직 목록)

| 항목 | 왜 불가능 | 하드웨어 도입 시점 |
|---|---|---|
| 실제 주기 지터 (µs) | 클록 드리프트·전기 노이즈는 실측 전용 | 필수 |
| 긴급정지 E2E 실측 응답 | 버스 전기 지연·인터럽트 지연 실체 | 필수 |
| IWDG 실동작 (고장주입 E1~E4) | 레지스터 카운터 실체 | 필수 |
| 전자기·온도·전원 영향 | 물리 현상 | — |

**결론**: 지금까지의 정적 증명(A~C)은 "실측을 하기 전에 할 수 있는 전부"이며,
Nucleo 한 대(~3만원)만 생기면 §3의 D/E와 실측 5종이 **같은 방법론으로 이어집니다**.
즉, 이 문서는 실측의 **대체가 아니라 전 단계**입니다.
