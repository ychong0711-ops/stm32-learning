# Architecture Decision: Enhanced GCC Verification Stub System

## Problem Statement

The current stub system includes only STM32F4-specific headers (`stm32f4xx_hal.h`). Mission templates increasingly use STM32F1 HAL direct calls (e.g., `HAL_GPIO_WritePin`, `HAL_UART_Transmit`), which fail compilation because:

- The `stm32f4xx_hal.h` stub defines types and functions optimized for F4 series
- F1 HAL headers have different type definitions, register layouts, and function signatures
- Users need to freely use HAL functions from "any STM32 project" without compilation errors

## Chosen Solution: Option A (Primary) + Option B (Supplementary)

### Option A: Bundled `stubs` Field in JSON

**Approach**: Add an optional `"stubs"` field to the mission bundle JSON containing custom stub header content. During compilation, build_server.py includes these bundled stubs after the base preamble, enabling per-mission HAL compatibility.

**Bundle JSON format**:
```json
{
  "stubs": [
    { "name": "stm32f1xx_hal.h", "content": "..." },
    { "name": "bsp_uart.h", "content": "..." }
  ],
  "files": [...],
  "missions": [...]
}
```

**Implementation in build_server.py**:
- When `b.stubs` is present, write each stub's content to `/home/user/stubs/`
- Append `#include "stub_name.h"` directives to the compilation prologue after the base headers
- gcc's existing `-I /home/user/stubs` flag resolves the includes

**Advantages**:
- Complete flexibility: any STM32 series HAL functions can be supported by writing appropriate stubs
- Per-mission compatibility: F1 missions get F1 stubs, F4 missions get F4 stubs
- Backward compatible: bundles without `stubs` field work exactly as before

**Disadvantages**:
- Requires server-side modification (build_server.py)
- Security consideration: arbitrary header upload via bundle (mitigated by validation)

### Option B: Series-Specific Stubs in make_stubs.py

**Approach**: Add `stm32f1xx_hal.h`, `stm32f0xx_hal.h` etc. as permanent stub files generated by make_stubs.py.

**Advantages**: No bundle modification needed for common series

**Disadvantages**: 
- HAL function signatures differ between series
- Finite coverage — cannot cover "all STM32" projects
- Maintenance burden for multiple series variants

### Decision

**Option A as primary, Option B as supplementary**.

Rationale: Option A achieves the "any STM32 project" goal by allowing each bundle to define its own stubs, while Option B provides ready-made stubs for common series without requiring bundle modifications. The combination gives both immediate usability (Option B stubs) and maximum flexibility (Option A).

## Changes Implemented

### 1. make_stubs.py — Added STM32F1 HAL Stub

New `stm32f1xx_hal.h` stub providing F1-compatible type declarations and function prototypes for common HAL functions used in F1 missions.

### 2. build_server.py — Bundle Stubs Integration

- `build_user_code()` now accepts optional bundle data
- When bundle contains `stubs` field, each stub's content is written to the STUBS directory
- Prologue includes `#include "stub_name.h"` after base headers
- Backward compatible: bundles without `stubs` field use existing behavior unchanged

### 3. Backward Compatibility

- Existing bundles without `stubs` field: no behavior change
- Existing stub files preserved — new stubs are written alongside
- Both F4 and F1 stubs can coexist; gcc includes them in order

## Verification Plan

1. **Existing mission submissions** pass without errors (backward compatibility)
2. **F1 HAL function usage** (e.g., `HAL_GPIO_WritePin`, `HAL_UART_Transmit`) in mission code compiles with F1 stubs
3. **F4 existing missions** still compile successfully with existing F4 stubs
4. **Bundle with stubs field** correctly includes and uses the bundled stub content
