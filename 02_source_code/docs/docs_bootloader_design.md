# 부트로더 · 펌웨어 갱신 설계 (셀프 플래싱 → 스테이징)

작성: 2026-08 / 대상: NUCLEO-F446RE (STM32F446RE, 512KB Flash, 128KB SRAM)

---

## 1. 무엇이 문제였나

이전 구조에서 애플리케이션은 `Bootloader_FlashNewFirmware()` 를 호출해
**자기 자신이 실행 중인 플래시 영역을 직접 지우고 다시 썼다.**

```
[앱 실행 중] → 앱 영역 erase → 앱 영역 write → reset
                     ↑
              이 시점에 전원이 끊기면?
```

이 방식에는 회복 불가능한 구간이 있다.

| 문제 | 내용 |
|---|---|
| **벽돌(brick) 구간** | erase 직후부터 write 완료까지, 플래시에는 실행 가능한 코드가 없다. 이 사이에 전원이 끊기거나 워치독이 물면 장치는 두 번 다시 부팅하지 못한다. 복구 방법은 SWD 디버거로 다시 굽는 것뿐이다. |
| **실행 중인 코드 삭제** | STM32F4 는 플래시 쓰기/소거 중 같은 뱅크에서의 명령어 인출이 멈춘다(stall). 지우는 코드가 지워지는 영역에 있으면 동작이 정의되지 않는다. RAM 함수로 옮기지 않는 한 성립하지 않는 구조다. |
| **검증 시점이 너무 늦음** | 이미지가 깨졌다는 사실을 알았을 때는 원본을 이미 지운 뒤다. 되돌릴 대상이 없다. |
| **롤백 불가** | 이전 버전이 남아 있지 않으므로 "실패하면 예전 걸로 돌아간다"가 불가능하다. |

즉 이전 구조는 **"쓰기가 성공한다"는 가정 위에서만** 동작했다. 안전 관련
시스템에서는 쓸 수 없는 가정이다.

## 2. 바꾼 구조: 스테이징 + 섹터 0 부트로더

핵심은 **받는 일과 설치하는 일을 분리**하고, 설치는 **자기 자신이 아닌 코드**가
하도록 만드는 것이다.

```
 ┌──────────────── 앱이 실행 중 ────────────────┐
 │ 1. 이미지를 수신해서 스테이징 영역에 기록    │  ← 앱 영역은 손대지 않음
 │ 2. CRC-32 로 전체 검증                       │  ← 깨졌으면 여기서 버리고 끝
 │ 3. "설치해줘" 요청을 백업 SRAM 에 기록       │
 │ 4. 소프트 리셋                               │
 └──────────────────────┬───────────────────────┘
                        ↓
 ┌──────────── 부트로더가 실행 (섹터 0) ────────┐
 │ 5. 요청 확인 + 스테이징 이미지 재검증        │  ← 설치 직전에 한 번 더
 │ 6. 앱 영역 erase → 스테이징에서 복사         │  ← 실행 중인 코드가 아님
 │ 7. 복사 결과를 다시 검증                     │
 │ 8. 앱으로 점프                               │
 └──────────────────────────────────────────────┘
```

6번 도중 전원이 끊겨도 괜찮다. 다시 부팅하면 부트로더가 먼저 돌고, 앱이
망가진 것을 발견하고, 스테이징 이미지는 그대로 남아 있으므로 복사를 처음부터
다시 한다. **벽돌 구간이 없다.**

## 3. 메모리 배치

STM32F446RE 의 512KB 플래시는 섹터 크기가 균일하지 않다. 섹터 0~3 이 16KB,
섹터 4 가 64KB, 섹터 5 부터 128KB 다. 플래시는 **섹터 단위로만 지울 수 있으므로**
경계를 섹터에 맞추는 것이 강제된다.

| 주소 | 크기 | 섹터 | 용도 |
|---|---|---|---|
| `0x08000000` | 16 KB | 0 | **부트로더** — 절대 지워지지 않는 영역 |
| `0x08004000` | 112 KB | 1~4 | **애플리케이션** |
| `0x08020000` | 128 KB | 5 | **스테이징** — 수신 이미지 임시 보관 |
| `0x08040000` | 256 KB | 6~7 | (미사용 — 향후 A/B 뱅크나 로그용) |
| `0x40024000` | 4 KB | — | **백업 SRAM** — 부트 제어 블록 (리셋으로 지워지지 않음) |

정의는 `bsp/flash_map.h` 한 곳에 있고, 링커 스크립트 2개와 호스트 도구
(`tools/make_image.py`, `tools/make_combined.py`)가 같은 값을 쓴다.

### 부트로더가 왜 섹터 0 인가
리셋 시 Cortex-M4 는 무조건 `0x08000000` 에서 초기 SP 와 Reset 벡터를 읽는다.
부트로더가 여기 있어야 **어떤 상황에서도 부트로더가 먼저 실행된다.** 앱이 완전히
망가져 있어도 부트로더는 멀쩡하므로 복구 경로가 항상 존재한다.

### 스테이징이 왜 섹터 5(128KB) 인가
앱 영역이 112KB 이므로 스테이징도 최소 그만큼 필요하다. 섹터 5 는 128KB
단일 섹터라서, 스테이징 전체를 **소거 한 번**으로 비울 수 있다. 여러 섹터에
걸치면 중간에 실패했을 때 상태가 애매해진다.

## 4. 이미지 포맷

앱 바이너리 앞에 32바이트 헤더를 붙인다 (`bsp/fw_image.h`).

| 오프셋 | 필드 | 설명 |
|---|---|---|
| `+0x00` | `ulMagic` | `0x4D465733` — 이게 펌웨어 이미지가 맞는지 |
| `+0x04` | `ulHeaderVersion` | `0x00010000` — 헤더 포맷 버전 |
| `+0x08` | `ulImageSize` | 본문 크기 (4의 배수) |
| `+0x0C` | `ulImageCrc32` | 본문 전체의 CRC-32 |
| `+0x10` | `ulFwVersion` | 펌웨어 버전 (`0x00010203` = v1.2.3) |
| `+0x14` | `ulLoadAddr` | 실행 주소 — 반드시 `0x08004000` |
| `+0x18` | `ulReserved` | 0 |
| `+0x1C` | `ulHeaderCrc32` | 앞 28바이트의 CRC-32 |

**헤더 CRC 를 따로 두는 이유**: 헤더가 깨졌으면 `ulImageSize` 도 못 믿는다.
크기를 믿고 본문 CRC 를 계산하려 들면 엉뚱한 범위를 읽는다. 그래서 헤더를
먼저 검증하고, 통과한 뒤에야 본문을 본다.

CRC-32 는 IEEE 802.3 (다항식 `0xEDB88320`, 초기값·최종 XOR `0xFFFFFFFF`) 이며,
`bsp/fw_image.c`(장치)와 `tools/make_image.py`(호스트)가 같은 값을 낸다.
`zlib.crc32()` 와도 일치하는 것을 확인했다.

### 벡터 테이블 온전성 검사
CRC 가 맞아도 "올바른 펌웨어"라는 보장은 없다. 예를 들어 부트로더 바이너리를
실수로 앱 이미지로 만들면 CRC 는 당연히 맞는다. 그래서 점프 직전에 한 번 더 본다.

- 초기 SP 가 SRAM 범위 (`0x20000000` ~ `0x20020000`) 안인가
- Reset 핸들러 주소의 **최하위 비트가 1** 인가 (Thumb 명령이므로 필수)
- Reset 핸들러 주소가 앱 영역 안을 가리키는가

세 조건 중 하나라도 어긋나면 점프하지 않는다. 잘못 점프하면 그 순간
하드폴트고, 부트로더까지 같이 죽는다.

## 5. 부트 제어 블록 (백업 SRAM)

앱과 부트로더는 리셋을 사이에 두고 대화해야 한다. "설치해줘"라는 요청과
"설치했어 / 실패했어"라는 응답을 주고받을 곳이 필요하다.

**백업 SRAM (`0x40024000`)** 을 쓴다. 소프트 리셋으로 지워지지 않으면서
플래시처럼 소거 과정이 필요 없다.

```c
typedef struct {
    uint32_t ulMagic;       // 0x5555AAAA — 블록이 초기화되었는지
    uint32_t ulRequest;     // 0x55504454('UPDT') = 설치 요청
    uint32_t ulAttempts;    // 설치 시도 횟수
    uint32_t ulLastResult;  // INSTALLED / RECOVERED / KEPT / FAILED
    uint32_t ulResetCount;  // 총 리셋 횟수
    uint32_t ulCheck;       // 위 필드들의 검사합
} BootCtrl_t;
```

`ulAttempts` 가 **부트 루프를 막는다.** 설치가 3번 연속 실패하면 부트로더는
더 시도하지 않고 `FAILED` 를 기록한 뒤 기존 앱으로 부팅한다. 이게 없으면
"설치 시도 → 실패 → 리셋 → 설치 시도 → ..." 를 영원히 반복한다.

`ulCheck` 는 백업 SRAM 이 전원 이상 등으로 오염되었을 때 쓰레기 값을 요청으로
오인하지 않기 위한 것이다.

## 6. 앱 쪽 변경 (`main_fixed.c`)

`vTask_Firmware` 가 하던 일이 바뀌었다.

**이전**:
```
안전 상태 진입 → 다른 태스크 정지 → vTaskSuspendAll()
→ 앱 영역 직접 erase/write → NVIC_SystemReset()
```

**지금**:
```
안전 상태 진입(PWM 0, FAN OFF) → 다른 태스크 정지
→ Bootloader_VerifyStaged() 로 스테이징 이미지 검증
   ├─ FW_IMAGE_OK      → 설치 요청 기록 후 리셋 (부트로더가 이어받음)
   └─ 그 외(검증 실패) → 실패 카운터 증가
                        → 정지시킨 태스크를 역순으로 재개
                        → 갱신 플래그 해제 (정상 운전으로 복귀)
```

핵심 차이는 **검증 실패가 더 이상 치명적이지 않다는 것**이다. 이전에는 이미
지운 뒤였지만, 지금은 아무것도 건드리지 않았으므로 그냥 하던 일로 돌아가면 된다.

`vTaskSuspendAll()` 도 없앴다. 플래시 쓰기는 수백 밀리초가 걸리는데 그동안
스케줄러를 멈추면 워치독이 물린다. 지금은 플래시를 만지는 주체가 부트로더라서
애초에 이 문제가 생기지 않는다.

### 워치독과의 관계
갱신 중에는 `xFirmwareUpdateActive` 플래그가 서고, 워치독 태스크는 이때
**다른 태스크의 하트비트를 기다리지 않고 무조건 IWDG 를 먹인다.** 정지시킨
태스크들이 하트비트를 못 보내는 것은 당연하므로, 이걸 고장으로 오인하면 안 된다.

## 7. 부트로더 동작 (`bootloader/boot_main.c`)

부트로더는 FreeRTOS 없이 도는 순수 베어메탈 코드다. 클록도 **HSI 16MHz 를
그대로 쓴다** — PLL 을 180MHz 로 올리지 않는다. 부트로더가 할 일은 플래시 복사와
점프뿐이라 속도가 필요 없고, 클록 설정이 단순할수록 실패 지점이 줄기 때문이다.
앱이 부팅하면 자기가 알아서 180MHz 로 올린다.

```
HAL_Init()
  → LED(PA5) 초기화              [상태 표시]
  → IWDG_Init(8000)              [복사가 오래 걸리므로 8초로 길게]
  → 백업 SRAM 접근 활성화
  → 부트 제어 블록 읽기
  → 설치할 것인가?
       조건: (설치 요청이 있거나 OR 현재 앱이 무효) AND 스테이징 이미지가 유효
       ├─ 예 → 시도 횟수 확인 (3회 이상이면 포기하고 FAILED)
       │        → 앱 영역 erase (섹터 1~4)
       │        → 스테이징 → 앱 영역 복사 (중간중간 IWDG 리로드)
       │        → 복사 결과 재검증
       │        → 결과 기록
       └─ 아니오 → 그대로 진행
  → 앱 이미지가 유효한가?
       ├─ 예 → 앱으로 점프
       └─ 아니오 → LED 를 빠르게 깜빡이며 대기 (복구 대기 상태)
```

### 점프 절차가 왜 이렇게 긴가

```c
HAL_RCC_DeInit();          // 클록을 리셋 기본 상태로
HAL_DeInit();              // 켜 둔 페리퍼럴 전부 원위치
__disable_irq();           // 이 아래로는 인터럽트가 오면 안 됨
SysTick->CTRL = 0;         // 타이머 정지 (안 끄면 점프 직후 SysTick 인터럽트)
SysTick->LOAD = 0;
SysTick->VAL  = 0;
for (i = 0; i < 8; i++) {  // 대기 중인 인터럽트까지 전부 정리
    NVIC->ICER[i] = 0xFFFFFFFF;
    NVIC->ICPR[i] = 0xFFFFFFFF;
}
SCB->VTOR = 0x08004000;    // 벡터 테이블을 앱 것으로
__DSB(); __ISB();          // 위 설정이 반영되기를 기다림
__set_MSP(*(uint32_t*)0x08004000);  // 앱의 초기 스택 포인터
__set_CONTROL(0);          // MSP 사용 · 특권 모드
__enable_irq();
((void(*)(void))(*(uint32_t*)0x08004004))();  // Reset 핸들러 호출
```

**앱은 자기가 첫 번째로 실행되는 코드라고 가정하고 짜여 있다.** 부트로더가
켜 놓은 페리퍼럴이나 인터럽트가 남아 있으면, 앱이 초기화를 마치기도 전에
인터럽트가 들어와 준비 안 된 핸들러로 점프한다. 그래서 남김없이 되돌린다.

`__DSB()`/`__ISB()` 는 Cortex-M 의 파이프라인 때문에 필요하다. `SCB->VTOR` 에
쓴 값이 실제로 반영되기 전에 다음 명령이 실행될 수 있어서, 명시적으로 동기화한다.

## 8. 앱의 VTOR 재배치

앱이 `0x08004000` 에 있으므로 벡터 테이블도 거기 있다. 그런데 하드웨어는
리셋 후 `SCB->VTOR = 0` (= `0x08000000`, 부트로더 벡터) 상태다.

부트로더가 점프 전에 `SCB->VTOR` 를 고쳐 주기는 하지만, **앱도 스스로 설정해야
한다.** 디버거로 앱을 직접 올려 실행하는 경우처럼 부트로더를 거치지 않는
경로가 있기 때문이다.

CMSIS 의 `system_stm32f4xx.c` 가 `SystemInit()` 에서 이 일을 해 주는데,
매크로로 켜야 한다. Makefile 의 앱 빌드에만 붙어 있다:

```
-DUSER_VECT_TAB_ADDRESS -DVECT_TAB_OFFSET=0x4000
```

이게 없으면 앱이 부트로더의 벡터 테이블을 계속 쓴다. `main()` 까지는 멀쩡히
도달하고, **첫 인터럽트가 발생하는 순간** 부트로더의 핸들러로 뛰어서 죽는다.
찾기 어려운 종류의 버그라 매크로 하나가 중요하다.

## 9. 호스트 도구

### `tools/make_image.py`
앱 바이너리에 32바이트 헤더를 붙인다. 장치에 보낼 파일을 만드는 도구다.

```bash
python3 tools/make_image.py -i build/app/app.bin -o app_image.bin --version 1.2.3
```

넘기기 전에 벡터 테이블 온전성도 검사한다. 엉뚱한 파일(예: 부트로더 바이너리)로
이미지를 만드는 실수를 호스트에서 미리 잡는다.

### `tools/make_combined.py`
부트로더와 앱을 하나로 합친다. 공장 출하나 초기 프로비저닝용이다.
사이의 빈 공간은 플래시 소거 상태와 같은 `0xFF` 로 채운다.

```bash
python3 tools/make_combined.py --boot boot.bin --app app.bin -o combined.bin
st-flash --reset write combined.bin 0x08000000
```

## 10. 남은 것 (정직하게)

| 항목 | 상태 |
|---|---|
| 서명 검증 (ECDSA 등) | 없음. CRC-32 는 **우연한 손상**만 잡는다. 악의적 변조는 못 막는다. 보안이 필요하면 서명이 따로 있어야 한다. |
| A/B 뱅크 롤백 | 없음. 섹터 6~7(256KB)이 비어 있어 자리는 있다. 지금은 "설치 실패 시 기존 앱 유지"까지만 된다. |
| 이미지 수신 경로 | CAN 으로 받는 실제 전송 프로토콜(분할·재전송·흐름 제어)은 미구현. `Bootloader_BeginStaging`/`WriteChunk`/`FinishStaging` 인터페이스만 준비됨. |
| 실제 하드웨어 검증 | **미수행.** 아래 §11 은 전부 정적/호스트 검증이다. |
